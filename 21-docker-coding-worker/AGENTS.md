# 🌌 ECHO Framework - Connaissance Sémantique : `21-docker-coding-worker`

> **ATTENTION AGENTS** : Ce document est la base de connaissances sémantique exclusive du dossier `21-docker-coding-worker`. Il complète les règles globales définies dans le `AGENTS.md` à la racine.

## 1. Rôle du Dossier

Ce dossier contient le code source de l'**API d'Exécution Multi-Langages Sécurisée & Terminal Interactif Sandbox (Coding Worker)**. Il s'agit d'un conteneur Docker isolé du reste du système. Son double rôle est :
1. **Exécution Batch Multi-Langages** : Recevoir du code (Python, JavaScript/Node.js, Bash `.sh`) généré par le LLM, installer dynamiquement ses dépendances (pip, npm), l'exécuter dans un environnement *Sandbox* restreint Bubblewrap (`bwrap`), et renvoyer le résultat (stdout/stderr).
2. **Terminal Interactif PTY WebSocket** : Fournir un shell pseudo-terminal interactif sécurisé (`/bin/bash --norc -i`) sous `bwrap` connecté nativement au composant Xterm.js d'Open WebUI (`XTerminal.svelte` via `routers/terminals.py`) sur `/api/terminals`.

## 2. Cartographie des Fichiers et Algorithmes

### `worker_api.py` (v6.25.1.1)
Fichier hybride combinant une API WSGI Flask et un serveur ASGI Starlette propulsé par `uvicorn` sur le port **5000**.
- **Architecture Hybride ASGI/WSGI (`asgi_app`)** : Enveloppe l'application Flask via `WSGIMiddleware` pour servir sans friction l'ensemble des routes HTTP existantes, tout en exposant avant `Mount("/")` les routes natives asynchrones `WebSocketRoute("/api/terminals/{session_id}")`, `WebSocketRoute("/ws/app/{run_id}[/{path:path}]")` (relais WS full-duplex TEXT/BINARY via `websockets` avec tâche `_touch_loop` rafraîchissant `last_activity_at` toutes les `60s`) et `Route("/app_proxy/{run_id}[/{path:path}]")` (proxy HTTP/SSE streaming `httpx.AsyncClient` sur UDS/TCP avec filtrage hop-by-hop, `read=None` si `Accept` demande `text/event-stream` sinon `300.0s`, rafraîchissement `last_activity_at` à chaque chunk et `X-Accel-Buffering: no` sur SSE).
- **Bus Mémoire & Serveur Socket Unix `CanvasRunHub`** : Serveur Socket Unix `AF_UNIX` par `run_id` (`/tmp/echo_ipc/{safe_rid}/ipc.sock` `chmod 0o666`, `ipc_dir` `chmod 0o755`, monté dans `bwrap` sur `/run/echo_ipc.sock`, avec repli `AF_INET` `127.0.0.1:0` -> `tcp://127.0.0.1:{port}`), prépare `app_sock_dir` (`{ipc_dir}/app`, `chmod 0o777`, monté sur `/run/echo_app`) et alloue un port TCP éphémère libre (`allocated_port != 5000`). Framing binaire symétrique `[uint32 BE meta_len][uint32 BE bin_len][UTF-8 JSON meta][raw bin]` strictement borné au contrat minimal : Sandbox -> Hub (`display` avec `"mode": "srcdoc"`, `expose_app` avec `"mode": "app_proxy"` et validation anti-traversal `os.path.basename` / port `1024..65535 != 5000` + `_verify_job_owns_tcp_port`), Hub -> Sandbox (`window_closed` uniquement). Émet de façon non-bloquante (`_notify_webui_sandbox_event`, thread démon `timeout=2.5s`, header `X-Echo-Callback-Token`) vers `ECHO_WEBUI_INTERNAL_URL/echo/v1/wm/internal/sandbox_event` les événements `frame_upsert` (quand `is_background=True`) et `run_finished` (dans `mark_job_finished` si `callback_token` et `(is_background or window_ids)`). `callback_token` est conservé uniquement en mémoire dans le dict `job` / `CanvasRunHub` et jamais injecté dans `bwrap`. Cycle de vie gouverné exclusivement par `idle_ttl_sec` (`1800s`) et `max_lifetime_sec` (`14400s`), avec nettoyage `/tmp/echo_ipc/{safe_rid}` à `mark_job_finished()`.
- **Endpoints HTTP Terminal & Découverte** :
  - `GET /api/config` : Retourne la déclaration des fonctionnalités terminales (`{"features": {"terminal": True, "files": False, "desktop": False, "browser": False}}`).
  - `GET /openapi.json` : Fournit la spécification OpenAPI minimale requise pour l'auto-découverte et la validation de connexion par Open WebUI.
  - `GET /api/terminals` : Liste les sessions actives filtrées par `user_id`/`chat_id` (`{"items": [TerminalSessionDict, ...], "count": int}`).
  - `POST /api/terminals` : Résout `user_id` et `chat_id` depuis les en-têtes (`X-User-Id`, `X-Session-Id` ou `X-Terminal-Context-Id`) ou le corps JSON, crée une session `local` (`agent_locked=False` par défaut) ou `ssh` (`agent_locked=True` forcé à l'ouverture, `bwrap` + `ssh -tt` via `_prepare_ssh_bwrap_auth(..., interactive=True)`) avec auto-nommage (`Terminal` / `<account_id>`) et retourne `TerminalSessionDict`.
  - `GET /api/terminals/<session_id>` : Retourne `TerminalSessionDict` (`404` si absente).
  - `GET /api/terminals/<session_id>/buffer` : Retourne la sortie nettoyée (`_strip_ansi_and_cr` via `read_clean_text`, `tail_lines` borné `1..500` par `TERMINAL_MAX_READ_LINES`, `since_cursor`), autorisé même sous verrou (`agent_locked=True`).
  - `POST /api/terminals/<session_id>/input` : Envoie une saisie ou un signal (`ctrl_c`, `ctrl_d`, `ctrl_z`, `enter`) avec attente `wait_ms` (`0..5000`), bloqué en **HTTP `423`** (`error_code="terminal_locked"`) lorsque `actor != "user"` et `agent_locked=True` (ou `409` si terminée).
  - `PATCH /api/terminals/<session_id>/lock` : Bascule `agent_locked` (`{"agent_locked": bool}`) et retourne `TerminalSessionDict`.
  - `DELETE /api/terminals/<session_id>` : Termine la session et nettoie `_ssh_tmp_dir` ; bloqué en **HTTP `423`** (`terminal_locked`) si `actor=agent` et `agent_locked=True`.
- **PTY WebSocket Bidirectionnel (`ws_terminal_endpoint`)** :
  - Handshake initial : Réception de la trame JSON `auth`, confirmation `chat` (`{"type": "chat", "chat_id": session.chat_id}`), vidage atomique d'`out_queue` et retransmission différentielle du buffer existant selon `resume`/`cursor` (sans doublon), puis fermeture WebSocket `code=1000` en fin de shell.
  - Protocole `XTerminal.svelte` : Émission de trames de contrôle `output` avec curseur de flux, streaming binaire des sorties du shell, support du redimensionnement de fenêtre (`resize` $\rightarrow$ `TIOCSWINSZ`), du heartbeat `ping`/`pong` et du re-binding dynamique `chat`.
- **Gestionnaire `TerminalSessionManager` & Fallback Multi-Plateforme** :
  - Sous Linux (`bwrap` + `pty`) : Ouvre un PTY maître/esclave via `pty.openpty()`, applique la taille initiale (80x24), configure le descripteur maître en non-bloquant, rattache `slave_fd` comme terminal de contrôle (`os.setsid()` + `TIOCSCTTY`) via `_spawn_session_process` et exécute soit le shell interactif local (`_build_interactive_bwrap_cmd`), soit `ssh -tt` isolé sous `bwrap` (`_prepare_ssh_bwrap_auth`).
  - Fallback portable : En l'absence de PTY ou bwrap (ex: exécution de test en `.venv` Windows), lance via `_spawn_session_process` un sous-processus interactif (`cmd.exe`, `/bin/sh` ou `ssh` si disponible) avec pipes standards et lecteur en thread dédié.
  - Maintient un buffer circulaire de 64 Ko (`max_buffer = 65536`), un curseur incrémental et un élagage automatique dans `_prune_sessions()` sur TTL d'inactivité (`TERMINAL_LOCAL_IDLE_TTL_SEC = 7200.0`, `TERMINAL_SSH_IDLE_TTL_SEC = 1800.0`) ou sessions mortes $> 300\text{s}$, avec suppression systématique de `_ssh_tmp_dir`.
- **Factorisation Bubblewrap (`_build_base_bwrap_cmd` & `_build_interactive_bwrap_cmd`)** :
  - Mutualise l'ensemble des montages de sécurité : isolation namespaces (`--unshare-ipc`, `--unshare-uts`, `--unshare-cgroup`, `--die-with-parent`), bascule utilisateur non privilégié (`--unshare-user --uid 65534 --gid 65534`), génération/montage `--ro-bind-try` de `/etc/passwd` et `/etc/group` (`_ensure_bwrap_identity_files`) pour `uid=65534`, montage RW de `/sandbox` (`--chdir /sandbox` ou `--chdir /sandbox/<sub_sid>` lorsque `sub_sid` est fourni), montages RO stricts de `/main`, `/plans`, `/generated`, `/files`, `/browserviews` et RW de `/.deps`. `_build_interactive_bwrap_cmd` configure également `PS1` (`sandbox:\w\$ `) et `PATH` (`/.deps/python/bin:/.deps/node/.bin:{PATH}`).
- **Endpoints HTTP Batch, Canvas & SSH** : Recherche de jobs factorisée via `_lookup_job(safe_uid, safe_cid, run_id="", prune=False)`. `/execute` (synchrone/background pour `.py`, `.js`, `.sh` et commandes Bash inline `command` sans création de fichier Codex avec validation syntaxique `bash -n -c`, lecture `callback_token` en mémoire uniquement, gestion du cycle de vie background par `idle_ttl_sec=1800s` et `max_lifetime_sec=14400s`, alignement `PATH` batch sur `/.deps/python/bin:/.deps/node/.bin:{PATH}`, injection `ECHO_RUN_ID`/`ECHO_IPC_SOCK`/`ECHO_APP_UDS`/`ECHO_APP_PORT`, montage `/run/echo_app` et exposition `canvas_frames`/`ui_ready`), `/app_proxy/{run_id}[/{path}]` & `/ws/app/{run_id}[/{path}]` (proxy interne HTTP/SSE streaming + WebSocket full-duplex vers les serveurs web sandboxés), `/ssh` (`POST`, validation et préparation factorisées via `_prepare_ssh_bwrap_auth(..., interactive=False, command=command)`, support clé privée `0o600`, certificat OpenSSH `id_key-cert.pub` et `sshpass` sous `bwrap`), `/status`, `/kill`, `/wait_ready` (`GET`, attente événementielle `ready_or_display_event` jusqu'à `15.0s`, retourne `canvas_frames`/`ui_ready`), `/canvas_signal` (`POST`, relais `window_closed` vers l'UDS avec grace killer `<= 3.0s`) et `/health`.

### ECHO Sandbox Monitor (`echo_monitor.py` & `echo_monitor.js` v6.17.4.1)
- **Sémantique & Transport Socket Unix (`ECHO_IPC_SOCK`)** : Bus mémoire Socket Unix `AF_UNIX` (`/run/echo_ipc.sock` ou `tcp://host:port`) avec framing binaire symétrique `[uint32 BE meta_len][uint32 BE bin_len][UTF-8 JSON meta][raw bin]` protégé par verrou d'écriture (`_IPC_WRITE_LOCK` / cycle `sock.ref()`/`sock.unref()` en Node.js) et export `_send_ipc_frame`/`send_ipc_frame`.
- **Surface Minimale (`display` + `expose_app`)** : Expose uniquement `display()` (HTML UTF-8 brut sans Base64), `is_window_closed()` (incluant EOF socket `_SOCKET_CLOSED`), `get_app_uds()`, `get_app_port()`, `wait_until_closed(window_id)`, `expose_app(...)` (boucle de readiness 50 ms UDS prioritaire puis TCP, émission `type: "expose_app"`, blocage événementiel optionnel) et `send_ipc_frame`. Lecteur entrant minimal ne traitant que `window_closed`.

## 3. Dépendances Logiques
- Ce Worker est invoqué par l'outil LLM `code_executor_tool.py` (situé dans `12-owui-tools`) pour les exécutions de scripts, et par le routeur backend Open WebUI `routers/terminals.py` pour les sessions interactives de `XTerminal.svelte`.
- Il n'a aucune persistance d'état propre : l'état est matérialisé dans le système de fichiers Codex de la session utilisateur.

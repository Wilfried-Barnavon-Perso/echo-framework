# 🌌 ECHO Framework - Connaissance Sémantique : `20-docker-admin-manager`

> **ATTENTION AGENTS** : Ce document est la base de connaissances sémantique exclusive du dossier `20-docker-admin-manager`. Il complète les règles globales définies dans le `AGENTS.md` à la racine.

## 1. Rôle du Dossier

Ce dossier contient l'application **ECHO Admin Manager**. Il s'agit d'un conteneur Docker isolé (Tier 4) offrant un panneau de contrôle (Dashboard) interactif. Son rôle est de surveiller l'état de santé du cluster Docker, de réguler l'infrastructure de base de données (SQLite/Qdrant) et de gérer les autorisations en temps réel de manière totalement découplée de l'interface de chat Open WebUI.

## 2. Cartographie des Fichiers et Algorithmes

L'application est structurée en **4 couches modulaires** orchestrées par le point d'entrée léger `server.py` (injection directe de l'instance Flask `app` sans `Blueprint` pour préserver les résolutions `url_for`).

### `server.py` (v5.226.18.0 - Point d'Entrée)
Initialise l'amorçage CPU (`psutil.cpu_percent`), démarre le singleton `backup_scheduler` (`BackgroundScheduler`), synchronise la planification (`update_system_schedules`) et lance le serveur Flask (`port=3001, debug=False, threaded=True`).

### Couche 2 : `services/` (Logique Métier & Tâches Asynchrones)
- **`services/semantic_pruning.py` (v6.18.3.1)** : Algorithme d'élagage temporel (`run_semantic_pruning`, `_run_semantic_pruning`), de purge synchrone par utilisateur (`purge_user_artifacts`, sans filtre de longueur arbitraire `len <= 30`), de purge des captures et clips MP4 `browserviews` éphémères déléguée à la fonction SSOT `cleanup_expired_browserviews_sync` (`echo_browser_lib.py` : grâce `BROWSER_TRANSIENT_GRACE_SEC = 1800.0s`, protection `retained` + `*_clip.mp4`, budget FIFO N2 et concurrence SQLite WAL/`BEGIN IMMEDIATE` via `EchoStateManager`, alimentée par un unique appel `GET {BROWSER_WORKER_URL}/sessions`), et de Garbage Collection des branches mortes (`gc_session_db`, `_delete_rag_points` avec purge Qdrant hybride message_id / uuid5) reposant sur `/app/backend/data/webui.db` (`table user`) comme **Single Source of Truth (SSoT)** avec une **politique Fail-Closed stricte** (3 verrous cumulatifs : Wait-for-it post-backup vérifiant `user` et `chat`, API Safeguard ECHO-UI appelant `/api/v1/users/` avec `follow_redirects=True`, et vérification `PRAGMA quick_check(1)` + présence de `admin@echo.local` + cartographie stricte par couple propriétaire `(user_id, chat_id)` via `user_valid_chats` et des fichiers valides `user_valid_file_ids` ; abandon immédiat sans suppression ni `VACUUM` si la base SSoT est injoignable ou verrouillée, ou si `pruning_error` capture une exception). Assure le GC fichiers FS dual-topologie ECHO v6 (`EchoStorageProvider` : nettoyage des dead symlinks dans `users/<uid>/files/` après purge de chat et protection des fichiers physiques hors-chat référencés dans `webui.db::file` + `Download Broker` : protection par `active_symlink_targets`), la vérification d'existence réelle (`os.path.isfile`, insensible aux dead symlinks) pour la purge de la table `file`, la purge des tables `webui.db` orphelines avec ou sans `user_id` (`auth`, `access_grant` en préservant le wildcard public `principal_id != '*'`, `automation_run`), le verrou d'intégrité `n8n_whitelist_complete`, la réconciliation des 5 volumes (`echo-webui-data`, `echo-qdrant-data`, `echo-download-broker-data`, `echo-n8n-data` via `/prune`, `echo-mcp-cache`), et le `VACUUM` sur `session.db`, `identity.db`, `webui.db`, `auth.db` et `database.sqlite` (N8N).
- **`services/memory_consolidation.py` (v5.226.18.0)** : Consolidation vectorielle Lvl1 → Lvl2 (`_cosine_sim`, `_centroid`, `consolidate_memories_for_user`) par clustering greedy et centroïde L2-normalisé (`"with_vector": True` sur `/points/scroll`, `"exact": True` sur `/points/count`) sans appel au worker d'embedding.
- **`services/maintenance_backup.py` (v6.18.0.1)** : Sauvegardes `tar.xz` à priorité minimale (`nice -n 19`, `ionice -c 3`, `XZ_OPT="-T2 -1"`, `IDLE_PRIORITY_CLASS`) incluant `echo-webui-data`, `echo-qdrant-data`, `echo-auth-data`, `echo-n8n-data` et `echo-mcp-cache` avec arrêt/redémarrage coordonné via `BACKUP_AUX_CONTAINERS` (`echo-webui`, `echo-qdrant`, `echo-n8n-worker`, `echo-mcp-broker`, `echo-download-broker`, `echo-coding-worker`, `echo-user-manager`), exécute un checkpoint WAL SQLite sur auth.db avant archivage, inclut SECRETS_DIR et HOST_ENV_FILE dans la sauvegarde tar.xz, suivi de progression temps-réel dans `MAINTENANCE_STATE` (`tar -cJf` via `psutil.Process.io_counters().read_bytes`, `sftp.put` via callback natif `_sftp_cb`, `rclone copy` via lecture de `/proc/<pid>/fdinfo` dans `_get_proc_file_offset`), création récursive `_sftp_mkdir_p`, construction unifiée du statut d'externalisation (`_build_ext_status_html`), retour structuré `backup_info` dans `perform_backup_task` et programmation APScheduler (`update_system_schedules`).

## 3. Dépendances Logiques
- L'Admin Manager s'exécute sur le port **3001** et monte directement le socket Docker (`/var/run/docker.sock`) ainsi que les bind-mounts `:ro` de ses 4 packages pour supporter le Hot-Reload (`echo.hot-reload=true`).
- Il partage les volumes `echo-webui-data`, `echo-qdrant-data`, `echo-auth-data`, `echo-backups`, `echo-download-broker-data`, `echo-n8n-data` et `echo-mcp-cache` afin d'exécuter ses routines de sauvegarde, restauration, réconciliation SSoT et d'optimisation SQLite/Qdrant/FS.

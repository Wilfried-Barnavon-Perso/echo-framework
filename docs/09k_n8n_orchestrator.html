9k. ECHO N8N Orchestrator

N8N Worker (Sandbox & Démon)

L'outil n8n_orchestrator_tool.py est le pont exclusif entre l'agent ECHO et le sous-système N8N Worker (Tier 2). N8N s'exécute de manière "Headless" sur SQLite (volume echo-n8n-data) via l'image n8nio/n8n native, adossée à Node.js.

Dichotomie Architecturale : Sandbox vs Démon

1. Sandbox Éphémère (Test & Développement) : Tout workflow créé dynamiquement par ECHO pour tester une logique doit obligatoirement commencer par un nœud Execute Workflow Trigger. Cela permet une exécution unitaire isolée (limitée à 64Ko pour les réponses synchrones). L'utilisation de données mockées (nœuds Code ou Set) est impérative pour simuler des webhooks sans exposer l'infrastructure réseau.

2. Déploiement Permanent (Démon) : Une fois le workflow validé, il peut être activé (Activation). Les triggers de type Webhook ou Cron/Schedule prennent le relais. Le workflow s'exécute de manière asynchrone en toile de fond. Ces workflows démons peuvent agir comme des clients MCP autonomes, et même initier de nouveaux "Child Chats" (threads de discussion dérivés) pour confier des sous-tâches complexes à d'autres agents ECHO, garantissant une traçabilité totale sans bloquer le flux principal.

Règles d'Architecture strictes

  • Sandbox Éphémère : Tout workflow testé dynamiquement par le modèle (pour résoudre un problème temporaire) doit OBLIGATOIREMENT démarrer par le nœud Execute Workflow Trigger. Le mocking de payload asynchrone est impératif pour simuler les Webhooks/Emails lors des tests LLM. Les exécutions synchrones étant limitées, le repli vers le mode asynchrone est souvent nécessaire.
  • Déploiements Permanents (Mode Démon) : Réservés aux webhooks de production et crons, destinés à tourner en arrière-plan indéfiniment. Ces workflows interagissent avec les outils externes.
  • Child Chats & MCP : Les workflows N8N en mode Démon agissent comme des clients MCP, requêtant les services d'ECHO et ouvrant asynchronement de nouveaux "Child Chats" dans le système ECHO pour exécuter des tâches LLM complexes avec traçabilité.
  • Identité & Secrets : L'usage en dur de tokens d'API ou Headers sensibles (Cookie, Authorization) dans les nœuds est strictement proscrit. L'outil exige l'usage de la macro __ECHO_SECRET_... qui est résolue via l'Identity Vault.

Orchestration Headless

L'orchestrateur N8N agit en mode démon pour des webhooks et des crons permanents. Cependant, lors des tests en sandbox via le CLI, tout workflow éphémère doit impérativement démarrer par un nœud Execute Workflow Trigger. Le système distingue radicalement les déploiements de production (permanents) de l'exploration interactive (sandbox).

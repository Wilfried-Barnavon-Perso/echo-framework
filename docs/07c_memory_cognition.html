7c. Cognition Profonde & Base vectorielle des souvenirs

Pour ne pas être qu'une simple calculatrice amnésique, ECHO s'appuie sur une mémoire vectorielle persistante et un moteur de routage cognitif dynamique.

Fiche d'Identité Technique

🧠 Cognition & Base vectorielle des souvenirs

Nature : Pipeline de Mémorisation (RAG Vectoriel) et Orchestrateur de Sous-Modèles.

Source : 11-owui-filters/conversation_memory_filter.py, 12-owui-tools/memory_tool.py, 12-owui-tools/cognitive_agents.py.

Rôle : Assurer la persistance à long terme des connaissances utilisateur (Préférences, Faits) et orchestrer le routage dynamique (LITE/FLASH/PRO) selon la complexité de la tâche.

Exécutant : Processus Python local (Backend) couplé à une base vectorielle Qdrant.

Interconnexions :

  • Input : Historique de conversation (distillé par Gemini Flash).
  • Stockage : Vecteurs 1024d (BAAI/bge-m3, local) insérés dans la collection echo_memory de Qdrant.
  • Output : Souvenirs réinjectés comme contexte textuel dans les outils de mémoire.

💡 Comprendre la Base vectorielle des souvenirs

ECHO possède deux cerveaux. Le premier est **Réactif** (le Cortex) : il décide instantanément s'il a besoin d'être "très intelligent" (modèle Pro) ou "très rapide" (modèle Flash). Le second est son **Registre** (la Base vectorielle des souvenirs) : c'est un carnet de notes numérique où il range vos préférences et les faits importants pour ne jamais les oublier, même dans une nouvelle discussion.

L'intelligence d'ECHO v5 repose sur une dualité fondamentale : le Cortex Réactif (Le Pipe) et le Registre Cognitif Persistant (La Mémoire). Cette architecture garantit une puissance de calcul maximale tout en préservant une cohérence historique absolue.

1. Architecture de la Ajustement du niveau cognitif (Le Cortex)

Le Pipe Engine (pipe_engine.py) n'est pas un simple tunnel de données. C'est un moteur de routage dynamique bidirectionnel qui gère la puissance de calcul en temps réel.

A. Cascade Native & Outil Virtuel d'Ajustement

Lors d'une requête en mode AUTO, ECHO initialise systématiquement la session sur MODEL_LITE (le point d'entrée par défaut). Cependant, le Cortex injecte dynamiquement un outil virtuel invisible pour l'utilisateur : new_cognitive_level.

Mécanique de l'Escalade & Redescente

Cet outil permet au modèle actuel de modifier sa propre puissance de calcul selon deux lois fondamentales :

  1. Loi de Nature de Tâche :
    • MODEL_LITE (Réflexe) : Salutations, extractions simples, culture générale basique.
    • MODEL_FLASH (Exécution) : Recherche web, scripts isolés, synthèse unitaire, outils simples.
    • MODEL_PRO (Expertise) : Architecture, orchestration, refactoring complexe, philosophie profonde.
  2. Loi de Corrélation Contextuelle (La Vallée de la Mort Contextuelle) : Plus le contexte (tokens) s'alourdit, plus le niveau cognitif doit augmenter pour maintenir la cohérence, indépendamment de la simplicité de la tâche. Si le contexte dépasse 50% de la fenêtre, le passage en MODEL_PRO est impératif.

B. Délégation Explicite (Expertise Conseil)

L'outil delegate_reasoning permet à l'orchestrateur de déléguer consciemment une portion de la tâche à un sous-système. Contrairement à la cascade native (qui change de modèle pour la réponse en cours), ici le résultat est réinjecté comme une donnée isolée, authentifiée par des ThoughtSignatures uniques présentes dans les logs système et les en-têtes de réponse.

🧠 Fonctionnement Stateless (Sans État)

La délégation cognitive est strictement éphémère. Le sous-modèle sollicité ne possède aucune mémoire des tours de parole précédents. Le paramètre context est donc obligatoire : il sert à injecter sémantiquement (format Markdown) tous les faits, souvenirs ou données nécessaires à la bonne exécution de la tâche isolée.

Modèle Cible Niveau de Pensée (Valve) Usage Recommandé (Délégation)
MODEL_PRO PRO_THINKING (HIGH) Debug de fichiers multiples, Planification multicouche.
MODEL_FLASH FLASH_THINKING (HIGH) Formatage JSON complexe, Traduction sémantique riche.
MODEL_LITE LOW Distillation de texte brut, Résumé de documents volumineux.

2. Base vectorielle des souvenirs V2 : La Reconstruction Bit-Perfect de l'Historique & Liant PRAF/PRAC

La mémorisation dans ECHO n'est pas un simple stockage de logs. C'est un pipeline de distillation vectorielle géré par le filtre conversation_memory_filter.py et exploité par l'Arsenal pour satisfaire aux principes de Rigueur Analytique (PRAF) et d'Amélioration Continue (PRAC).

A. Le Cycle de Mémorisation (Non-bloquant)

Le déclenchement est piloté par deux facteurs : la probabilité (TRIGGER_PROBABILITY=0.1) et le seuil de sécurité (FORCE_TRIGGER_THRESHOLD=20 messages).

💡 Pourquoi 10% de probabilité ?

Pour ne pas saturer le backend après chaque phrase (ce qui ralentirait l'IA inutilement), la mémorisation se déclenche aléatoirement avec 10% de chances par tour court, MAIS se déclenche obligatoirement tous les 20 messages via le seuil de sécurité pour garantir la capture du contexte long.

Une fois déclenché, le pipeline s'exécute en tâche de fond :

Pipeline Technique de Mémorisation

1. Distillation (Gemini 2.5 Flash) -> Génère un JSON (Summary, Importance 1-5, Slug, Tags)
2. Vectorisation (BAAI/bge-m3 — Local) -> 1024 Dimensions, Distance: Cosine
3. Recherche (Qdrant) -> Similarité Seuil 0.85
4. Action :
   - Similitude < 0.85 : Création d'un nouveau point vectoriel.
   - 0.85 < Similitude < 0.95 : Fusion LLM (Ancien + Nouveau) pour mise à jour sémantique.
   - Similitude > 0.95 : Simple "Touch" (Mise à jour du timestamp de rétention).

B. Gouvernance des Données & TTL (Time To Live)

Chaque souvenir possède une date d'expiration. Les durées de rétention (TTL) par niveau d'importance sont configurables dynamiquement via le Dashboard de l'Admin Manager, permettant une gestion fine de l'atrophie mémorielle :

  • Niveau 1 (Trivial) : Souvenirs éphémères et informations de passage.
  • Niveau 2 (Mineur) : Contexte de session étendue.
  • Niveau 3 (Utile) : Préférences techniques et noms de projets.
  • Niveau 4 (Majeur) : Logique métier stable et décisions d'architecture.
  • Niveau 5 (Axiome) : Règles de sécurité et Principes ECHO fondamentaux.

C. Consolidation Automatique des Souvenirs (Centroïde Vectoriel)

Après la purge TTL, l'Admin Manager exécute une consolidation des souvenirs Triviaux (Niveau 1) quand leur nombre dépasse un seuil configurable (défaut : 10 par utilisateur).

💡 Pourquoi consolider les souvenirs Triviaux ?

Les souvenirs lvl1 s'accumulent rapidement : chaque session peut en générer plusieurs. Ils sont pénalisés au rappel (poids 0.55 vs 1.00 pour lvl3) et occupent de l'espace vectoriel à faible valeur unitaire. La consolidation fusionne les faits sémantiquement proches en connaissances de niveau 2 (Mineur, poids 0.75), plus stables et mieux pondérées.

Mécanisme : Clustering Greedy + Centroïde Vectoriel

Exemple concret avec 3 souvenirs lvl1 d'un même utilisateur :

Situation de départ dans Qdrant
Point A (lvl1)  summary: "L'utilisateur préfère le thème sombre dans toutes les interfaces."
                vector:  [0.12, -0.45, 0.78, ...] (1024 valeurs normalisées L2)

Point B (lvl1)  summary: "L'utilisateur déteste les popups et notifications intrusives."
                vector:  [0.15, -0.41, 0.80, ...]

Point C (lvl1)  summary: "L'utilisateur préfère les interfaces épurées, sans éléments superflus."
                vector:  [0.11, -0.43, 0.77, ...]
Pipeline de consolidation (Admin Manager)
1. SCROLL lvl1 with_vectors=true
   → Récupération des 3 points avec leurs vecteurs complets (aucun appel embedding)

2. CLUSTERING GREEDY
   cos(A,B) = 0.81 ≥ 0.75  → B rejoint le cluster d'A
   cos(A,C) = 0.84 ≥ 0.75  → C rejoint le cluster d'A
   Taille cluster = 3 ≥ min_cluster_size(3) ✓

3. CALCUL DU CENTROÏDE (dimension par dimension, Python pur)
   centroïde[0] = (0.12 + 0.15 + 0.11) / 3 = 0.127
   centroïde[1] = (-0.45 + -0.41 + -0.43) / 3 = -0.430
   centroïde[2] = (0.78 + 0.80 + 0.77) / 3 = 0.783
   ...
   Re-normalisation L2 → vecteur_final (sur la sphère cosinus, valide pour Qdrant)

4. CRÉATION DU POINT FUSIONNÉ (lvl2)
   vector:             vecteur_final (centroïde normalisé)
   summary:            "L'utilisateur préfère le thème sombre [...] |
                        L'utilisateur déteste les popups [...] |
                        L'utilisateur préfère les interfaces épurées [...]"
                        ↑ concaténation COMPLÈTE — aucune troncature
   memory_importance:  2  (promotion lvl1 → lvl2)

5. SUPPRESSION des 3 anciens points lvl1
   POST /points/delete  {"points": [id_A, id_B, id_C]}

   Résultat :  3 points lvl1  →  1 point lvl2
               3 slots Qdrant →  1 slot Qdrant
               pondération recall : ×0.55 → ×0.75

🛡️ Propriétés garanties

  • Aucune troncature : le summary stocké contient l'intégralité des textes originaux.
  • Aucun appel réseau supplémentaire : les vecteurs sont déjà présents dans le scroll Qdrant. Le worker bge-m3 n'est pas sollicité pendant la consolidation.
  • Aucun appel Gemini : pas de dépendance aux clés API utilisateur. L'opération est 100% locale.
  • Idempotence : une consolidation sur des points déjà consolidés (lvl2) ne produit aucun effet (le scroll filtre strictement memory_importance=1).

Décision Architecturale : Pourquoi seulement Lvl1 → Lvl2 ?

🏛️ Principe : Respecter le Jugement du LLM de Distillation

La consolidation automatique est délibérément limitée aux souvenirs Triviaux (Niveau 1). Ce choix est une décision architecturale, pas une limitation technique.

Transition Consolidation auto ? Raison
Lvl1 → Lvl2 (Trivial → Mineur) ✅ Oui Accumulation rapide, faible valeur unitaire, gain de compression élevé.
Lvl2 → Lvl3 (Mineur → Utile) ⚠️ Discutable Lvl2 est déjà une connaissance qualifiée par le LLM. Fusionner automatiquement risque de diluer des distinctions intentionnelles.
Lvl3 → Lvl4 (Utile → Majeur) ❌ Non Le score a été assigné délibérément par le LLM de distillation. Une promotion automatique contourne ce jugement.
Lvl4 → Lvl5 (Majeur → Axiome) ❌ Jamais Les Axiomes sont des vérités fondamentales désignées explicitement. Toute promotion automatique serait une corruption de l'ontologie mémorielle.

Règle d'or : La consolidation automatique ne peut qu'élever des souvenirs de faible certitude vers le niveau immédiatement supérieur. La promotion des niveaux Utile, Majeur et Axiome reste une prérogative exclusive du LLM de distillation.

Les trois paramètres de consolidation sont configurables dans le Dashboard Admin Manager, panneau "Élagage & Cycle de Vie" :

  • Seuil déclenchement : nb de lvl1 par user avant consolidation (défaut : 10).
  • Taille cluster min : nb minimum de souvenirs similaires pour fusionner (défaut : 3).
  • Seuil cosinus : similarité minimale pour appartenir au même cluster (défaut : 0.75).

3. Interaction Cortex / Registre

L'IA utilise l'outil memory_tool.py pour interroger son registre. Cela permet de décider *quand* elle a besoin de contexte historique, évitant ainsi le "bruit" dans la fenêtre de contexte actuelle.

Action UI : Purge Granulaire

Pour une gouvernance totale, l'utilisateur peut déclencher manuellement l'action ECHO Memory Purge. Elle permet de visualiser les catégories de souvenirs (tags) triées par importance et fréquence, de sélectionner des plages de données (ex: 1-5, 8) et de procéder à un oubli sélectif sécurisé via un mode Dry Run (prévisualisation des impacts).

🧠 Gérer la Purge Mémoire

✅ Le point sur l'exactitude (Mémoire)

La logique de mémorisation vectorielle et le cycle de vie (TTL) sont pilotés de manière asynchrone par l'Admin Manager. L'action de purge granulaire dans purge_memory_action.py utilise un filtrage Qdrant strict sur les tags sélectionnés, garantissant qu'aucune donnée collatérale n'est effacée.

Spécifications Qdrant

  • Collection : echo_memory
  • Partitionnement : Isolation stricte par user_id via payload filter.
  • Indexation : HNSW pour une recherche ultra-rapide.
